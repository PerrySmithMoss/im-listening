## Task 3 — Implement secure Google sign-in with OAuth 2.0 / OpenID Connect

Build on Tasks 1 and 2. Add Google registration and sign-in alongside email/password authentication, using OIDC to establish identity and the existing Express/Redis session for access to Im Listening. The checklist below is the acceptance criteria; review the linked guidance again during implementation.

- [x] Record the authentication flow, trust boundaries, library choice, and account/recovery policy in a short design note. Use a maintained OIDC library compatible with the server runtime. Benchmark the user journey against [Slack's documented Google sign-in experience](https://slack.com/intl/en-gb/help/articles/212681477-Sign-in-to-Slack) and account linking against [Auth0's published precautions](https://auth0.com/docs/manage-users/user-accounts/user-account-linking). Explain which patterns apply here and distinguish documented behaviour from assumptions about those products' internals.
- [x] Implement server-side Authorization Code flow with PKCE (`S256`), cryptographically random `state` and `nonce`, and server-side code exchange. Store short-lived, browser-bound transactions in Redis, consume them atomically once, and reject missing, expired, mismatched, or replayed transactions. Handle concurrent login attempts safely. Require exact registered callback URLs, HTTPS in production, and allowlisted local return paths; derive public URLs from trusted configuration. Do not use implicit/password grants or silently downgrade PKCE. Follow [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) and the [OWASP OAuth guidance](https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html).
- [x] Validate ID tokens on the server through the library: signature and allowed algorithm, Google's trusted issuer, this environment's client ID audience, `azp` where applicable, expiry, issued-at time with bounded clock skew, and the transaction's nonce. Use trusted Google discovery/JWKS with caching and key rotation; never accept endpoints supplied by the browser. Fail closed on validation or provider failures. Follow [Google's OIDC documentation](https://developers.google.com/identity/openid-connect/openid-connect).
- [x] Add a Prisma external-identity relation keyed uniquely by canonical Google issuer and `sub`, linked to the existing internal user ID. Create/link accounts transactionally with database uniqueness constraints. Support Google-only accounts without fabricated passwords, collect a unique username and any missing required profile fields, and retain existing users, posts, and profiles. Email and display names must not serve as provider identity keys.
- [x] Require a verified email before using it as the account's contact address, and define additional ownership verification for non-Gmail/non-Workspace addresses where Google is not authoritative. Do not overwrite an existing account's email or recovery settings automatically. Cover these distinctions using [Google's email-authority and ID-token guidance](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).
- [x] Make linking an explicit authenticated action requiring recent proof of control of both accounts. Never automatically merge accounts because emails match, even when Google reports a verified email. Handle existing-email collisions without exposing account details or granting access. Require reauthentication and CSRF protection for unlinking, prevent removal of the last usable sign-in method, and define safe password setup/recovery for Google-only accounts so password reset cannot silently bypass the linking policy. Apply the [Auth0 account-linking precautions](https://auth0.com/docs/manage-users/user-accounts/user-account-linking).
- [x] Extend the Vercel same-origin proxy and Express session middleware to cover authentication routes, including the callback. Regenerate and save the session after authentication; preserve `sessionVersion` invalidation. Keep the production `__Host-im-listening` cookie `Secure`, `HttpOnly`, host-only, and `Path=/`, with an explicitly tested `SameSite` policy compatible with the Google redirect. Define idle and absolute expiry, enforce CSRF protection for authenticated mutations, and make logout destroy the local session. Verify against [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
- [x] Request only `openid email`, adding `profile` only for fields the product needs. Do not request offline access or retain Google tokens for sign-in alone. Keep tokens and client secrets out of browser storage and client bundles. If Google API access is later needed, design incremental consent, encrypted server-side token storage, revocation, and deletion separately. Follow [Google's OAuth best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices).
- [ ] Use the `imlistening.emails@gmail.com` Google account to create and manage the Google Cloud project(s), OAuth clients, and consent configuration. Configure separate development/staging/production OAuth clients, isolate production credentials, and register exact origins/callbacks without wildcard preview domains. Complete consent branding, verified domains, privacy/terms links, and any required Google verification. Store the production client secret as a Docker secret with documented rotation. Update environment examples and the VPS runbook, including proxy configuration, local setup, and an image rollback procedure that preserves existing password access.
- [x] Add an accessible, mobile-friendly Google button on login and registration using [Google's approved branding](https://developers.google.com/identity/branding-guidelines). Provide clear loading, cancellation, retry, account-selection, linking, and onboarding states. Return users to a validated intended page without redirect loops or unnecessary repeat consent prompts. Keep existing email/password journeys working.
- [ ] Rate-limit initiation, callback, and linking routes; bound provider timeouts and fail safely during Google/Redis outages. Record redacted authentication/linking outcomes and monitor failures. Exclude codes, tokens, secrets, cookies, and unnecessary personal data from application, proxy, analytics, and error logs. Serve callback responses with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, avoid third-party resources there, and redirect promptly to a clean URL.
- [x] Add automated integration/security tests with a mock OIDC provider for successful registration/login, returning users, concurrent callbacks, missing profile fields, email/username collisions, safe linking/unlinking, and Google-only recovery. Reject forged/expired tokens, wrong issuer/audience/nonce, state or PKCE failures, callback replay, open redirects, login CSRF, session fixation, and account takeover through email matching. Test JWKS rotation, provider/Redis failures, logout, expiry, and session invalidation. CI must not depend on live Google credentials.
- [ ] Run the existing API/client checks and regression tests for password login, registration, reset, and post ownership. Verify the complete Google flow in desktop/mobile browsers through the deployed Vercel-to-VPS route, including cancellation, persistence after reload, cookie behaviour, and logout. Complete a focused security review against the design note and linked guidance, and record rollout/rollback evidence before marking the task complete.
