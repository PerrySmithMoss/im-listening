# Google sign-in design

## Browser, API and Google

Login and registration offer the same Google account chooser alongside password authentication. First-time Google users complete an Im Listening profile. Returning users go directly to the home page or the post they started from. Slack documents a comparable choice between email and Google, followed by account selection. Its workspace and SSO steps are specific to Slack. The comparison concerns the published user journey. [Slack sign-in help](https://slack.com/intl/en-gb/help/articles/212681477-Sign-in-to-Slack)

1. The browser initiates a same-origin JSON POST through the Vercel rewrite. Express requires the exact configured origin and creates a five-minute Redis transaction keyed by the session ID hash and random state. Each transaction also holds its own random nonce and S256 PKCE verifier. The configured frontend origin determines the exact callback URL. Return paths are limited to home and numeric post routes.
2. Google returns the authorization response as a form POST. The API holds it in Redis for up to 60 seconds and redirects with an opaque receipt. The browser's follow-up GET carries the Lax session cookie. The API consumes the transaction with Redis `GETDEL` under that session's key and deletes the receipt. A per-session completion slot prevents concurrent valid callbacks from issuing competing sessions. Both callback hops use no-store and no-referrer and carry no third-party resources. [Google OIDC reference](https://developers.google.com/identity/openid-connect/reference) · [Vercel log fields](https://vercel.com/docs/drains/reference/logs)
3. The API exchanges the code using `openid-client` v6, which runs under the repo's Node 26 CommonJS build. The library discovers metadata from the fixed canonical Google issuer, requires advertised S256, checks state and nonce, and verifies the RS256 signature against cached, rotating JWKS. It validates issuer, audience and expiry. The app also checks `azp` when supplied and accepts issuance up to five minutes old with 30 seconds of skew. Requests to discovery, token and JWKS endpoints have a five-second timeout. The app requests only `openid email` and discards the Google tokens after validation. [openid-client](https://github.com/panva/openid-client) · [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) · [OWASP OAuth guidance](https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html) · [Google OAuth best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices)

## Accounts and recovery

- PostgreSQL owns account state. The unique pair `https://accounts.google.com` and `sub` maps to an internal user ID. A user can connect one Google identity. Registration writes the user, profile and identity in one transaction. Required profile fields are entered locally.
- New accounts require Google-verified email. A Gmail address or a Google Workspace hosted-domain claim is sufficient for initial contact verification. Other addresses require an eight-digit code sent to the mailbox. A returning or linked account keeps its existing email and recovery settings. A duplicate email blocks new registration with generic guidance to use the existing sign-in method. [Google email authority](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)
- Connecting Google starts from the signed-in account's settings. It requires the current Im Listening password and fresh Google authorization with explicit account selection within five minutes. Google may use its existing browser session for that authorization. An identity already attached to another internal account cannot be transferred through this flow. Disconnecting Google requires the current password, which also ensures a usable method remains. Connecting, disconnecting and setting a password increment the session version transactionally. [Auth0 account linking precautions](https://auth0.com/docs/manage-users/user-accounts/user-account-linking)
- Google-only accounts have a null password. Password reset ignores these accounts. To add a password, a signed-in user authorizes the same Google subject again and proves current access to the existing contact mailbox. Ordinary password reset becomes available after password setup. A user who has lost Google access before setting a password needs to recover their Google account.

## Sessions and trust

The browser holds an opaque session ID in a host-only `__Host-im-listening` cookie with Secure, HttpOnly, Path=/ and SameSite=Lax. Redis stores the session with a 24-hour idle TTL. The server enforces a seven-day absolute limit and checks the PostgreSQL session version on authenticated requests. Successful authentication rotates and saves the session. Logout destroys it. JSON write requests with browser session cookies must come from the exact configured origin. The Google callback is protected by the browser-bound transaction, PKCE and nonce. [OWASP session guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

Redis also stores the expiring OAuth transactions and callback receipts, mailbox code digests and rate-limit counters. PostgreSQL stores accounts and identity links. Audit messages contain fixed outcome labels. See the [VPS runbook](deploy-vps.md) for logging and rollout checks.
